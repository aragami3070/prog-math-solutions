# Rust Knowledge

Первый работающий срез: **Axum + PostgreSQL + HTML-скрапер с очередью обхода + React/TypeScript**.

- `/` — собранные документы с пагинацией, кратким текстом, ссылкой на оригинал и признаком полноты.
- `/stats` — документы по источникам, объём текста, полнота, запросы/ошибки и последние запуски.
- `/swagger-ui/` — OpenAPI и ручной запуск сбора. Просмотр сайта сам по себе ничего не скрапит.

Текущая архитектура и границы: [.agent/rust-knowledge/current-slice.md](.agent/rust-knowledge/current-slice.md). Дальнейший план: [.agent/README.md](.agent/README.md). Tantivy, Qdrant, ML и JSONL/CSV-export **ещё не реализованы**. Обход HTML-ссылок реализован; массовый сбор пока не запускался.

Backend разделён на router → use case → repository (SQLx) → PostgreSQL в Docker Compose. Зоны `crawls`, `sources` (включая документы), `statistics`, `health` разделены на каждом слое; каждый use case — отдельный файл. Router передаёт транзакцию в use case и коммитит после успеха, repository работает в ней. Ошибки находятся в соседних `errors.rs`. Фоновый сбор использует короткие транзакции вне сетевых запросов.

## Локальный запуск

Команды выполняются из `/home/aragami3070/ssu/term7/prog-math-solutions`. Нужны Rust toolchain с поддержкой зависимостей из `Cargo.lock`, Node.js ≥22.12 и PostgreSQL. Проверено с Rust 1.98.1, Node 26.9 и PostgreSQL 18.6; Compose предлагает PostgreSQL 17. Не считаем минимальную поддерживаемую версию Rust измеренной.

```sh
# Только при первой настройке, если .env ещё не существует:
cp .env.example .env

docker compose up -d --wait postgres
npm --prefix web ci --ignore-scripts
npm --prefix web run build
cargo run --locked
```

Открыть <http://127.0.0.1:8080>. Axum раздаёт собранный фронт; миграции применяются при запуске. Для frontend HMR в другом терминале: `npm --prefix web run dev`, затем адрес Vite из вывода. `/api` и `/swagger-ui` проксируются к backend на 8080.

Все настройки редактируются в `.env` в корне проекта; образец — [.env.example](.env.example). Backend автоматически читает файл при запуске до создания Tokio runtime и настройки логов. После изменения файла перезапустите backend. Переменные, уже заданные в окружении процесса, имеют приоритет. Отсутствующий файл допустим, ошибка чтения/синтаксиса завершает запуск без вывода его содержимого. `.env` исключён из Git.

API работает локально без авторизации. `HTTP_BIND` принимает только loopback-адреса (`127.0.0.1` или `::1`); по умолчанию `127.0.0.1:8080`. Пустой `CRAWLER_USER_AGENT` выключает сбор, просмотр остаётся доступным. `rks/rks` — только локальные credentials. Авторизация для внешнего развёртывания — будущая задача.

## Первый сбор

1. Ознакомиться с текущими robots/условиями источника, указать **свой действительный** контакт в User-Agent.
2. В `.env` задать `CRAWLER_USER_AGENT` вида `"RustKnowledgeCollector/0.1 (+mailto:ВАШ_КОНТАКТ)"`. Placeholder не является контактом; не отправлять его сайту.
3. Перезапустить backend командой `cargo run --locked`. Выполнить `POST /api/crawls` через Swagger UI или curl:

```sh
curl -i http://127.0.0.1:8080/api/crawls \
  -H 'Content-Type: application/json' \
  --data '{"source":"rfc"}'

curl http://127.0.0.1:8080/api/stats
curl 'http://127.0.0.1:8080/api/documents?page=1&page_size=20'
```

`202` означает **запуск принят**, не успешную загрузку. Результат появится в последних запусках `/api/stats`. Для Internals отправьте `{"source":"internals"}`. На главной странице также есть выбор источника и кнопка «Начать сбор»: она вызывает ту же ручку. Состояние обновляется каждые 5 секунд.

`requested` в запуске теперь означает число поставленных в очередь страниц, которое растёт по мере обнаружения ссылок. `succeeded` — обработанные страницы (включая списки), `failed` — страницы с ошибкой. Осталось в очереди: `requested - succeeded - failed`. Число уникальных документов считается отдельно. Raw HTML хранится в `fetches`, разобранный текст — в `documents`, план обхода — в `crawl_queue`.

Лимита в 20 URL больше нет. Обход начинается с главной страницы выбранного ресурса. Из HTML извлекаются ссылки на документы, списки, продолжения и оглавление RFC в iframe; разрешённые URL добавляются в PostgreSQL-очередь. Переходы ограничены известными HTML-маршрутами того же источника, параметры — пагинацией. Якоря и варианты slug нормализуются; `(run_id, url)` исключает повторную постановку. Поиск, профили, служебные URL, внешние ссылки и другие книги на rust-lang.github.io не обходятся. Единственный сборщик на одну БД, пауза минимум 5 секунд перед **каждым** запросом, включая robots и redirects. `Crawl-delay` может увеличить паузу. Robots загружается при каждом запуске; timeout/5xx/неожиданный HTML не считается разрешением. `404` означает только отсутствие robots, не разрешение владельца на любой сбор.

На первом `403`/`429` или распознанном challenge сбор прекращается, источник сохраняется как paused в БД. Повторных попыток, proxy rotation и маскировки под браузер нет. После ручной проверки причины и выдержанного `Retry-After` можно разрешить новый запуск:

```sh
curl -i -X POST http://127.0.0.1:8080/api/sources/rfc/resume
```

`resume` снимает только паузу источника и не запускает сбор автоматически. После этого повторный `POST /api/crawls` продолжит незавершённую очередь. Этот механизм не является способом обхода отказа. Отсутствие блокировок гарантировать нельзя.

## Проверки

```sh
cargo fmt --all --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
npm --prefix web test
npm --prefix web run build
```

Интеграционные тесты отдельно: SQLx создаёт изолированные БД и применяет миграции. Использовать **локальный тестовый PostgreSQL**, роль должна иметь `CREATEDB`; не указывать production:

```sh
cargo test --locked --test storage -- --ignored
```

SQLx также читает `DATABASE_URL` из `.env`.

SQL-запросы используют compile-time макросы `query!`, `query_as!` и `query_scalar!`. В `.env` и шаблоне задано `SQLX_OFFLINE=true`: обычная сборка использует сохранённые в `.sqlx/` метаданные и не подключается к PostgreSQL. Этот режим влияет на компиляцию; запущенному серверу БД всё равно нужна.

После изменения SQL или миграций обновите метаданные по актуальной локальной схеме. Нужен SQLx CLI той же версии 0.8.6:

```sh
docker compose up -d --wait postgres
cargo sqlx migrate run
cargo sqlx prepare -- --all-targets --locked
cargo sqlx prepare --check -- --all-targets --locked
```

CLI берёт `DATABASE_URL` из `.env`; `prepare` включает проверку по живой БД на время команды. Обновлённые файлы `.sqlx/` сохраняются в Git вместе с запросами и миграциями. SQL оформляется многострочными блоками, параметры SQLx и ответы/параметры utoipa — отдельными строками.

Тесты не обращаются к Internals/RFC. HTML в `tests/fixtures` синтетический и не входит в собранный корпус. Проверяются парсеры, URL/robots, API/OpenAPI, локальный адрес сервера, пагинация и frontend errors; интеграционные тесты — SQL, upsert, raw HTML, блокировка, persistent pause, восстановление interrupted runs, rollback/commit нескольких use cases и реальные HTTP handlers.

## Ограничения первого среза

- Собираются страницы, достижимые по поддерживаемым HTML-ссылкам. Это не гарантия нахождения всех страниц сайта. Продолжения Internals объединяются в одну тему с дедупликацией постов, однако полный состав темы независимо не проверен: completeness остаётся unknown. Счётчики **не подтверждают** 5 000 полных тем.
- Очередь сохраняется в БД. После рестарта запуск становится interrupted; повторный POST того же источника продолжает его, повторяя failed и pending страницы, но не done. Автоматического retry нет. После успешного завершения следующий POST начинает новый обход.
- JSON списка — UI-проекция с excerpt, **не полный экспорт** корпуса. Полный raw HTML хранится в PostgreSQL; API его не исполняет и не выдаёт как HTML.
- 2026-10-17 проверены robots (Internals 200, RFC 404), HTML главной, разметка тем и ссылка `?page=2` длинной темы Internals. Это точечная проверка разметки, не сквозная проверка полного обхода. Массовый сбор не запускался.
- Численные показатели качества поиска/ресурсов отсутствуют. Browser QA (мобильная ширина, клавиатура, реальная навигация) требует отдельного прогона; build и HTTP-проверки его не заменяют.
