# Rust Knowledge

Первый работающий срез: **Axum + PostgreSQL + HTML-скрапер с очередью обхода + React/TypeScript**.

- `/` — собранные документы с пагинацией, кратким текстом, ссылкой на оригинал и признаком полноты.
- `/stats` — документы по источникам, объём текста, полнота, запросы/ошибки и последние запуски.
- `/swagger-ui/` — OpenAPI и ручной запуск сбора. Просмотр сайта сам по себе ничего не скрапит.

Текущая архитектура и границы: [.agent/rust-knowledge/current-slice.md](.agent/rust-knowledge/current-slice.md). Дальнейший план: [.agent/README.md](.agent/README.md). Реализованы HTML-обход и экспорт JSON/JSONL/CSV/ZIP. Tantivy, Qdrant и ML **ещё не реализованы**.

Backend разделён на router → use case → repository (SQLx) → PostgreSQL в Docker Compose. Зоны `crawls`, `sources` (включая документы), `statistics`, `health` разделены на каждом слое; каждый use case — отдельный файл. Router передаёт транзакцию в use case и коммитит после успеха, repository работает в ней. Ошибки находятся в соседних `errors.rs`. Фоновый сбор использует короткие транзакции вне сетевых запросов.

## Локальный запуск

Команды выполняются из `/home/aragami3070/ssu/term7/prog-math-solutions`. Нужны Rust toolchain с поддержкой зависимостей из `Cargo.lock`, Node.js ≥22.12 и PostgreSQL. Проверено с Rust 1.98.1, Node 26.9 и PostgreSQL 18.6; Compose предлагает PostgreSQL 17. Не считаем минимальную поддерживаемую версию Rust измеренной.

```sh
# Только при первой настройке, если .env ещё не существует:
cp .env.example .env

docker compose up -d --wait postgres
npm --prefix web ci --ignore-scripts
npm --prefix web run build
cargo run --locked
```

Открыть <http://127.0.0.1:8080>. Axum раздаёт собранный фронт; миграции применяются при запуске. Для frontend HMR в другом терминале: `npm --prefix web run dev`, затем адрес Vite из вывода. `/api` и `/swagger-ui` проксируются к backend на 8080.

Все настройки редактируются в `.env` в корне проекта; образец — [.env.example](.env.example). Backend автоматически читает файл при запуске до создания Tokio runtime и настройки логов. После изменения файла перезапустите backend. Переменные, уже заданные в окружении процесса, имеют приоритет. Отсутствующий файл допустим, ошибка чтения/синтаксиса завершает запуск без вывода его содержимого. `.env` исключён из Git.

API работает локально без авторизации. `HTTP_BIND` принимает только loopback-адреса (`127.0.0.1` или `::1`); по умолчанию `127.0.0.1:8080`. Пустой `CRAWLER_USER_AGENT` выключает сбор, просмотр остаётся доступным. `rks/rks` — только локальные credentials. Авторизация для внешнего развёртывания — будущая задача.

## Первый сбор

1. Ознакомиться с текущими robots/условиями источника, указать **свой действительный** контакт в User-Agent.
2. В `.env` задать `CRAWLER_USER_AGENT` вида `"RustKnowledgeCollector/0.1 (+mailto:ВАШ_КОНТАКТ)"`. Placeholder не является контактом; не отправлять его сайту.
3. Перезапустить backend командой `cargo run --locked`. Выполнить `POST /api/crawls` через Swagger UI или curl:

```sh
curl -i http://127.0.0.1:8080/api/crawls \
  -H 'Content-Type: application/json' \
  --data '{"source":"rfc"}'

curl http://127.0.0.1:8080/api/stats
curl 'http://127.0.0.1:8080/api/documents?page=1&page_size=20'
```

`202` означает **запуск принят**, не успешную загрузку. Результат появится в последних запусках `/api/stats`. Для Internals отправьте `{"source":"internals"}`. На главной странице также есть выбор источника и кнопка «Начать сбор»: она вызывает ту же ручку. Состояние обновляется каждые 5 секунд.

`requested` в запуске теперь означает число поставленных в очередь страниц, которое растёт по мере обнаружения ссылок. `succeeded` — обработанные страницы (включая списки), `failed` — страницы с ошибкой. Осталось в очереди: `requested - succeeded - failed`. Число уникальных документов считается отдельно. Raw HTML хранится в `fetches`, разобранный текст — в `documents`, план обхода — в `crawl_queue`.

Лимита в 20 URL больше нет. Обход начинается с главной страницы выбранного ресурса. Из HTML извлекаются ссылки на документы, списки, продолжения и оглавление RFC в iframe; разрешённые URL добавляются в PostgreSQL-очередь. Переходы ограничены известными HTML-маршрутами того же источника, параметры — пагинацией. Якоря и варианты slug нормализуются; `(run_id, url)` исключает повторную постановку. Поиск, профили, служебные URL, внешние ссылки и другие книги на rust-lang.github.io не обходятся. Страница темы или RFC, скачанная не более `CRAWL_FRESH_DAYS` дней назад (по умолчанию 7, `0` выключает), повторно не запрашивается: ссылки берутся из сохранённого в `fetches` HTML, пауза не тратится. Это же касается продолжения незавершённого обхода. Страницы-списки (`/latest`, категории) качаются всегда, чтобы находить новые темы. Тема, в которую дописали посты, обновится, когда истечёт окно. Единственный сборщик на одну БД, пауза минимум 5 секунд перед **каждым** запросом, включая robots и redirects. `Crawl-delay` может увеличить паузу. Robots загружается при каждом запуске; timeout/5xx/неожиданный HTML не считается разрешением. `404` означает только отсутствие robots, не разрешение владельца на любой сбор.

На первом `403`/`429` или распознанном challenge сбор прекращается, источник сохраняется как paused в БД. Страница, которую сайт называет несуществующей (404/410, например мёртвая ссылка в оглавлении), не считается сбоем: она помечается `missing`, считается отдельно в запуске (`missing`), не повторяется при продолжении и не запрашивается заново в окне `CRAWL_FRESH_DAYS`. После `403`/`429` повторов нет, как нет и proxy rotation или маскировки под браузер. Временные сбои (обрыв соединения, таймаут, ответы 502/503/504) повторяются до трёх попыток с паузами 10 и 20 секунд сверх обычной задержки; если источник остаётся недоступным пять страниц подряд, запуск завершается как `failed`, а остальная очередь остаётся ожидающей. Продолжить можно обычным `POST /api/crawls`. После ручной проверки причины и выдержанного `Retry-After` можно разрешить новый запуск:

```sh
curl -i -X POST http://127.0.0.1:8080/api/sources/rfc/resume
```

`resume` снимает только паузу источника и не запускает сбор автоматически. После этого повторный `POST /api/crawls` продолжит незавершённую очередь. Этот механизм не является способом обхода отказа. Отсутствие блокировок гарантировать нельзя.

## Граф связей

`POST /api/graph/rebuild` строит рёбра `references` из таблицы `links` (ссылка из поста на другой документ корпуса; якоря и сноски внутри документа — не рёбра; фрагмент хранится как свидетельство). `GET /api/graph?document=rfc:3058&limit=100` отдаёт соседей на один шаг: кто ссылается и на кого, с URL ссылок, `truncated` и временем построения. Граф не зависит от Qdrant и моделей. Рёбра `has_topic` и `similar_to` пока не строятся. Страница «Связи» показывает соседей списками (Cytoscape не подключён).

## Поиск

Лексический поиск (baseline B0): индекс Tantivy строится из PostgreSQL, к сайтам-источникам не обращается. Индекс не обновляется сам: после сбора перестройте его (старый индекс отвечает, пока строится новый; пересборка занимает секунды).

```bash
curl -X POST http://127.0.0.1:8080/api/search/rebuild
curl 'http://127.0.0.1:8080/api/search?q=async+fn'
curl 'http://127.0.0.1:8080/api/search?q=RFC+3058'
curl 'http://127.0.0.1:8080/api/search?q=%22generic+associated+types%22&source=internals&complete_only=true'
```

Запрос: слова (ИЛИ с весом BM25, название ×3), `"фраза"` по позициям, номер документа (`rfc:3058`, `RFC 3058`, `3058`; точный ID идёт первым). Токенизатор сохраняет `?`, `!`, `'`, `::`, `->`, идентификаторы и не удаляет стоп-слова; без стемминга. Необязательные режимы (по одному изменению, каждый измерен `eval`): `fuzzy=true` — исправление опечаток по словарю корпуса, `synonyms=true` — таблица синонимов/аббревиатур (`SYNONYMS_VERSION`), `lemmas=true` — другие формы слова по таблице лемм (`tools/lemmas`, `LEMMA_FILE`). Они только добавляют ветки с меньшим весом, исходные слова остаются, а ответ перечисляет все исправления и расширения (`rewrite`); фразы в кавычках не переписываются. `total` — все совпавшие документы индекса, глубже 1000 результатов выдача недоступна. Ответ называет поколение индекса и версию анализатора; индекс другой версии анализатора не открывается, его надо перестроить. Каталог индекса — `SEARCH_INDEX_DIR` (по умолчанию `data/index`, в git не попадает); хранятся текущее и одно предыдущее поколение. Страница «Поиск» на сайте использует тот же API.

`mode=vector|hybrid` — смысловой поиск: чанки постов (`tools/nlp/embed_corpus.py`, модель `intfloat/multilingual-e5-small`) лежат в Qdrant (`docker-compose --profile vectors up -d qdrant`), вектор запроса считает локальный `tools/nlp/worker.py`; hybrid сливает лексический и векторный top-100 через RRF. Фильтры `source`/`complete_only` одни и те же в обеих половинах. Векторные режимы отдают не более 100 кандидатов (`total_is_pool`). Если Qdrant или воркер недоступны, ответ лексический, а `scope.degraded` говорит почему. Подготовка Python-окружения — `tools/lemmas/README.md`.

## Онлайн-оценка (A/B)

Эксперимент `hybrid-vs-b0` v1 зафиксирован в коде (`src/experiment/mod.rs`) до любого трафика: B0 (лексический) против hybrid, 50/50, первичная метрика — доля сессий, где есть клик без немедленной переформулировки (в течение 60 с), минимальный интересный эффект — 5 п.п., α = 0.05, мощность 0.8. Изменение любого параметра — новая версия. `GET /api/experiment[?session=…]` отдаёт конфиг и группу сессии.

- **Назначение.** Клиент делает случайный `session` (8–64 символа `A-Za-z0-9_-`) и передаёт его в `/api/search?session=…`. Группа — `sha256(experiment:version:session) mod 10000`; тест фиксирует стабильность и долю. В эксперименте группа сама задаёт `mode`, а fuzzy/synonyms/lemmas выключаются: одно изменение за эксперимент.
- **События** (таблица `search_events`, без IP и User-Agent): `search` пишется сервером (запрос, режим, фильтры, число результатов, задержка, `degraded`, поколение индекса) и возвращает `experiment.query_id`; `POST /api/events/click {query_id, document_id, rank}` берёт сессию и группу из записи поиска, клиент их подменить не может. Переформулировка и «без клика» выводятся при анализе из последовательности событий. Сбой записи не ломает ответ поиска.
- **Анализ.** `cargo run --bin eval -- online-report --db yes` (или `--events файл.jsonl`) → `eval/online/<name>.{md,json}`. Единица — сессия; доверительные интервалы bootstrap (2000 ресэмплов, фиксированное зерно); p по Welch z; для вторичных метрик — поправка Бонферрони; SRM-проверка χ² (флаг при p < 0.001); требуемый размер выборки; срезы по типу первого запроса (RFC ID, идентификатор, английский, русский) только при ≥100 сессиях в каждой группе; гардрейлы (p95 задержки, нулевая выдача, degraded). Вердикт включает «различий не обнаружено» и «выборки недостаточно».
- **Проверка конвейера.** `online-simulate` генерирует синтетические события; три отчёта в `eval/online/synthetic-*.md` (эффект есть / эффекта нет / слишком мало сессий) показывают, что анализ различает эти случаи. Это проверка кода, не свидетельство о качестве поиска: реального трафика пока нет, реальных выводов тоже.
- **Не сделано.** Team-draft interleaving (альтернатива при малом трафике) и учёт ошибок 5xx в событиях (ошибки видны только в логах сервера); фронтенд пока не генерирует `session` и не шлёт клики (его нельзя собрать на этой машине).

## Экспорт корпуса

Внизу страницы статистики `/stats` есть блок «Экспорт корпуса». Можно скачать JSONL, JSON, CSV или ZIP со всеми тремя форматами и `manifest.json`. Экспортирует все документы выбранного источника, а не текущую страницу каталога. По умолчанию включены partial/unknown; флажок «Только подтверждённо полные» исключает их (например, темы, у которых ещё не скачана следующая страница).

```sh
curl --fail --show-error 'http://127.0.0.1:8080/api/sources/export?format=zip' -o corpus.zip
curl --fail --show-error 'http://127.0.0.1:8080/api/sources/export?format=jsonl&source=internals' -o internals.jsonl
curl --fail --show-error 'http://127.0.0.1:8080/api/sources/export?format=json&source=rfc&complete_only=true' -o rfc.json
curl --fail --show-error 'http://127.0.0.1:8080/api/sources/export?format=csv&spreadsheet_safe=true' -o corpus.csv
```

Контракт: `GET /api/sources/export`. `format=jsonl` по умолчанию; `source` можно не задавать, либо `internals`/`rfc`; `complete_only=false`; `spreadsheet_safe=false`. Неизвестные параметры и форматы возвращают 400. Полный контракт — в Swagger и [.agent/rust-knowledge/data.md](.agent/rust-knowledge/data.md).

JSON/JSONL содержат полные тексты, стабильные ID (`internals:42`, `rfc:3058`), sections, ссылки, доступное авторство/даты, provenance, parser version и hash. Неизвестные данные не придумываются: язык, категория и идентификаторы лицензий пока null, отсутствие тегов/авторов — пустые массивы. Сохраняется исходный `metadata`. Raw HTML и исторические версии в экспорт не входят.

CSV сохраняет кавычки, запятые и переводы строк; вложенные значения записаны JSON в ячейках. По умолчанию текст неизменён. `spreadsheet_safe=true` добавляет апостроф перед потенциальными формулами в строковых ячейках CSV; JSON/JSONL это не меняет. Для импорта в электронные таблицы выбирайте этот режим.

ZIP содержит `corpus.jsonl`, `corpus.json`, `corpus.csv`, `manifest.json`. Manifest фиксирует версию схемы (1), время снимка, фильтры, количество документов по источникам/полноте, версии парсеров и SHA-256 файлов. `corpus_sha256` равен SHA-256 `corpus.jsonl`. ZIP сейчас без сжатия. Заголовки отдельных файлов: `X-Corpus-Schema-Version`, `X-Corpus-Documents`, `X-Corpus-Snapshot-At`, `X-Content-SHA256`.

Сбор может продолжаться: экспорт читает один repeatable-read snapshot, порциями по 32 записи в порядке `document_id` (C collation). Router открывает и завершает транзакцию. Перед отправкой формируется временный файл; затем транзакция закрывается, браузер скачивает файл потоково. Память не зависит от размера всего корпуса; нужны место во временном каталоге и память для порции документов. Для ZIP во время упаковки одновременно хранятся три формата и архив. Временные файлы удаляются при закрытии, ошибки или отмена не оставляют постоянных артефактов. Одновременно один процесс готовит один экспорт (второй получает 409). Скачивание готового файла не занимает слот подготовки.

Для появления новой ручки перезапустите backend (`cargo run --locked`); frontend соберите через `npm --prefix web run build`, если используете раздачу Axum. Незавершённый обход после рестарта продолжайте привычной кнопкой. Экспорт сам не обращается к внешним сайтам.

## Модель данных и перепарсинг

`documents` — тема или RFC. `document_pages` — одна строка на HTTP-страницу темы (`/t/42`, `/t/42?page=2`), `posts` — один пост (текст хранится только здесь), `links` — ссылки поста с текстом якоря. `documents.body_text`, `content_hash` и `completeness` — производные: пересчитываются из постов и страниц при каждом сохранении страницы. Сырой HTML остаётся в `fetches`.

Перед миграциями рабочей БД и по расписанию делайте дамп: `scripts/backup.sh [метка]`. Он пишет проверенный дамп (`pg_restore --list`) и `.sha256` в `~/backups/rust-knowledge/`, при `BACKUP_MIRROR=/другой/диск` копирует его туда и хранит `BACKUP_KEEP` (14) последних дампов без метки; дампы с меткой не удаляются. Восстановление: `pg_restore -d "$DATABASE_URL" --clean --if-exists файл.dump`.

## Проверки

```sh
cargo fmt --all --check
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
npm --prefix web test
npm --prefix web run build
```

Интеграционные тесты отдельно: SQLx создаёт изолированные БД и применяет миграции. Использовать **локальный тестовый PostgreSQL**, роль должна иметь `CREATEDB`; не указывать production:

```sh
cargo test --locked --test storage --test export -- --ignored
```

SQLx также читает `DATABASE_URL` из `.env`.

SQL-запросы используют compile-time макросы `query!`, `query_as!` и `query_scalar!`. В `.env` и шаблоне задано `SQLX_OFFLINE=true`: обычная сборка использует сохранённые в `.sqlx/` метаданные и не подключается к PostgreSQL. Этот режим влияет на компиляцию; запущенному серверу БД всё равно нужна.

После изменения SQL или миграций обновите метаданные по актуальной локальной схеме. Нужен SQLx CLI той же версии 0.8.6:

```sh
docker compose up -d --wait postgres
cargo sqlx migrate run
cargo sqlx prepare -- --all-targets --locked
cargo sqlx prepare --check -- --all-targets --locked
```

CLI берёт `DATABASE_URL` из `.env`; `prepare` включает проверку по живой БД на время команды. Обновлённые файлы `.sqlx/` сохраняются в Git вместе с запросами и миграциями. SQL оформляется многострочными блоками, параметры SQLx и ответы/параметры utoipa — отдельными строками.

Тесты не обращаются к Internals/RFC. HTML в `tests/fixtures` синтетический и не входит в собранный корпус. Проверяются парсеры, URL/robots, API/OpenAPI, локальный адрес сервера, пагинация и frontend errors; интеграционные тесты — SQL, upsert, raw HTML, блокировка, persistent pause, восстановление interrupted runs, rollback/commit нескольких use cases и реальные HTTP handlers.

## Ограничения первого среза

- Собираются страницы, достижимые по поддерживаемым HTML-ссылкам. Это не гарантия нахождения всех страниц сайта. Продолжения Internals (`?page=N`) хранятся постранично и собираются в одну тему. Полнота — это цепочка страниц: `complete`, если собраны страницы 1…N подряд и у последней нет ссылки на следующую; `partial`, если страницы не хватает или у последней есть next. Это «полно на момент скачивания»: число постов у источника независимо не сверяется, а тема потом может вырасти. Повторный обход заменяет только перезагруженную страницу и не урезает уже собранное.
- Очередь сохраняется в БД. После рестарта запуск становится interrupted; повторный POST того же источника продолжает его, повторяя failed и pending страницы, но не done. Автоматический повтор есть только для временных сетевых сбоев (см. выше); упавшие страницы по-прежнему возвращаются в очередь повторным POST. После успешного завершения следующий POST начинает новый обход.
- JSON списка — UI-проекция с excerpt; полный текст доступен через `/api/sources/export`. Raw HTML хранится в PostgreSQL и в экспорт не входит.
- 2026-10-17 проверены robots (Internals 200, RFC 404), HTML главной, разметка тем и ссылка `?page=2` длинной темы Internals. Это точечная проверка разметки, не сквозная проверка полного обхода. Массовый сбор не запускался.
- Численные показатели качества поиска/ресурсов отсутствуют. Browser QA (мобильная ширина, клавиатура, реальная навигация) требует отдельного прогона; build и HTTP-проверки его не заменяют.
