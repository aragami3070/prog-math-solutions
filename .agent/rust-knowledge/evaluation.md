# Оценка поиска и моделей

## Основной метод для домашки

Offline evaluation по graded relevance. На небольшом учебном сайте A/B-тест без достаточного трафика малоубедителен; основной результат не зависит от появления пользователей. Клики и dwell time — поздние шумные сигналы, не готовая разметка.

Шкала для пары query/document:

- **2 — релевантно:** документ существенно отвечает информационной потребности; нужный RFC по номеру либо прямой разбор вопроса.
- **1 — слабо релевантно:** относится к теме и даёт полезный контекст, но не отвечает на основной вопрос.
- **0 — нерелевантно:** не помогает запросу или только случайно содержит термины.

Непроверенное — `unjudged`, не 0. Для запросов про актуальный статус нужен актуальный источник; старый проект не получает 2 лишь потому, что совпало название возможности.

## Набор и протокол

1. Зафиксировать corpus snapshot, не менее 60 запросов с intent/языком; ориентир 100. Срезы: RFC IDs, identifiers, English prose, Russian prose, опечатки, синонимы, формы слов, фильтры, no-answer.
2. Dev/test разделять по семействам информационной потребности; близкие перефразировки и typo-версии одного запроса держать в одной группе. Финальный test не используется для весов, synonyms, thresholds или prompt tuning.
3. Для каждого запроса собрать pool top-20 из B0 и улучшенных систем, объединить по document ID, добавить вручную найденные положительные и отрицательные примеры. Перемешать; скрыть score/rank/название системы от разметчика.
4. Сохранить qrels с assessor type/version и evidence; часть не менее 20% разметить независимо вторым человеком, если доступен. Если человек один, честно указать это, не придумывать inter-annotator agreement.
5. LLM может сделать предварительную разметку, но human-reviewed holdout минимум 20 запросов и их top-10 кандидатов обязателен для внутреннего контроля проекта. Не использовать одну модель как классификатор и единственного судью без анализа смещения.
6. Для спорных меток зафиксировать итог и причину; переоценку не делать выборочно только там, где любимая система проиграла.

Артефакты: `queries.jsonl` (query_id/text/intent/language/filters/split), `qrels.tsv` (query_id/document_id/grade), `judgments.jsonl` (provenance/evidence), `runs/<variant>.tsv` (query_id/document_id/rank/score), `report.json` и Markdown-отчёт с corpus/model/config hashes.

## Метрики и ограничения

- nDCG@10: gain `2^grade−1`, discount `log2(rank+1)`; основная graded метрика. Явно описать политику unjudged и judgment coverage@10. До headline-сравнения доразметить объединённый top-10 сравниваемых систем, а не тихо считать пропуски нерелевантными.
- P@10: релевантными считать grade≥1, отдельно strict P@10 для grade=2. Если результатов меньше 10, недостающие позиции не дают gain.
- MRR@10: reciprocal rank первого grade=2, иначе 0.
- Recall@10 по pool — только **pooled recall**, не полнота относительно всего неизвестного корпуса. Указывать denominator и ограниченность разметки.
- Запросы без известных релевантных документов выделять отдельно; nDCG с IDCG=0 не смешивать без пояснения с обычным средним. Отдельно считать ложные положительные и корректные пустые ответы.
- p50/p95, throughput, память, latency NLP/vector, деградации; холодный/прогретый индекс раздельно, hardware и concurrency зафиксированы.

Сравнения: B0; B0+typo; B0+synonyms; B0+lemma; vector-only; hybrid; hybrid+AI-topic metadata (если влияет на ranking). Помимо поэтапного варианта нужна абляция отдельных изменений. Считать macro по запросам, отдельно срезы; при достаточном размере — paired bootstrap по query groups с seed. Отрицательный результат допустим.

## LLM-судья

Одинаковый rubric, blind shuffled pairs, фиксированные модель/prompt/revision, bounded JSON output с grade/evidence. Не передавать ranking score и желаемый результат. Не выполнять инструкции внутри документов. При усечении документа отмечать coverage, не выдавать мнение по фрагменту за оценку полного текста. Измерить согласие с ручными метками; автоматические qrels маркировать silver.

Классификация оценивается отдельно (macro/micro F1, per-topic показатели, abstention), граф — precision по типу рёбер. Не переносить хорошую поисковую nDCG на качество тегов или графа.

## Онлайн-оценка: A/B-тесты и поведенческие метрики (P10)

Делается в самом конце, после P8: offline-результат остаётся основным, онлайн его дополняет. Если трафика нет, этап сводится к методике, симуляции и честному выводу «выборки недостаточно», а не к выдуманным числам.

**События** (без персональных данных, session ID случайный и короткоживущий): `search` (query_id, variant, mode, filters, generation, число результатов, latency), `click` (query_id, document_id, rank), `reformulate`, `no_click`. Логировать на сервере, не хранить сырые IP и User-Agent.

**Назначение варианта:** детерминированный хэш от session ID и ID эксперимента, один пользователь видит один вариант. Конфиг эксперимента версионирован: варианты, доли трафика, даты, гипотеза, первичная метрика, минимально значимый эффект. Параметры и метрики фиксировать до запуска, не подбирать после просмотра результатов.

**Что сравнивать:** B0 против лучшего варианта из P4/P5 (например hybrid); по одному изменению за эксперимент.

**Метрики**
- Первичная: success rate сессии поиска (есть клик на результат и нет немедленной переформулировки) либо MRR по первому клику.
- CTR@k, позиция первого клика, доля запросов без кликов (abandonment), доля переформулировок, zero-result rate.
- Dwell time — только как шумный вспомогательный сигнал, не как relevance label.
- Guardrails: p95 latency, доля ошибок и degraded-режимов, zero-result rate не должен вырасти.

**Анализ:** sanity-проверка распределения трафика (SRM, χ²) до интерпретации; единица анализа — сессия или пользователь, не отдельный запрос (иначе зависимые наблюдения); доверительные интервалы bootstrap'ом по пользователям либо z-тест долей; поправка при нескольких метриках; рассчитать нужный размер выборки заранее. Результаты считать для срезов (English/Russian, RFC ID, identifiers) только если по срезу достаточно данных.

**Interleaving** (team-draft) как альтернатива при малом трафике: чувствительнее A/B, т.к. оба варианта показываются в одной выдаче. Требует событий клика с атрибуцией варианта; результат — доля побед варианта, а не абсолютная метрика.

**Ограничения:** клики смещены позицией и сниппетом; рост CTR не равен росту relevance; малая аудитория учебного сайта даёт широкие интервалы. Offline nDCG и онлайн-метрики сравнивать между собой и описывать расхождения, отрицательный результат фиксировать. Согласие с offline-выводом — отдельный пункт отчёта.

**Приёмка:** описанный и воспроизводимый план эксперимента, работающее логирование и назначение вариантов (тест на стабильность хэша), скрипт анализа на синтетических или реальных событиях, отчёт с интервалами, SRM-проверкой и выводом, включая «различий не обнаружено».
