# Темы, теги и классификация

## Цель

Multi-label классификация документов по темам. Не генерация бесконечных похожих тегов и не определение того, что реально стабилизировано в Rust. Сначала исходные category/tags форума, затем отдельные машинные метки.

Таксономия уточняется на пилоте и хранится в `tools/nlp/topics-v*.json`. В v3 добавлены `documentation` и `ffi-platform-compatibility`, а `standard-library` заменена широкой темой `libraries` для стандартных и внешних библиотек; `modules-paths` появилась в v2. Старые версии и присвоенные по ним метки сохраняются отдельно: переименование или объединение не меняет их задним числом. Несколько меток допустимы; `unclassified` означает недостаток основания. Определения и границы тем проверяются на пилоте.

## Модель и workflow

Выбран кандидат `gemini-4-hydrogen-low` через agy. Качество, лимиты и стоимость предстоит проверить; вызов отправляет документы внешнему сервису. Пользователь разрешил ограниченный пилот через agy с учётом риска: проверенный `agy --sandbox` сам по себе инструменты не отключает. Для пилота используется пустой рабочий каталог, sandbox и не включается автоматическое разрешение действий. Это не гарантирует полного отключения инструментов. Локальный Qwen пока не используется.

1. Создать ручной набор 100–200 документов, включая длинные и пограничные случаи, и простой baseline по source tags/ключевым словам.
2. Zero/few-shot классификация с закрытой taxonomy, JSON-контрактом и разрешённым отказом от решения. Fine-tuning не нужен для первого запуска.
3. Для короткого документа передавать title + основной текст; для длинного — разделы/посты по токен-бюджету, затем агрегировать метки по подтверждающим фрагментам. Не ограничиваться заголовком или первой страницей. Записывать долю реально обработанного текста.
4. Валидировать ID тегов, лимит 1–5 тем (или ни одной), существование section IDs и точность evidence quotes относительно входа. Невалидный JSON — ограниченный retry, затем review, а не сохранение произвольной строки.
5. Сохранить model ID + revision, tokenizer, runtime/quantization, prompt/taxonomy version, decoding params, content hash, coverage, результат и review state.
6. Человек может принять/отклонить/добавить метку. Ручное решение не затирается повторным запуском модели и хранится отдельным событием.

Выход: document ID/hash, topics[{topic_id, evidence_section_ids, evidence_quotes}], status (`proposed|reviewed|unclassified|failed`), provenance. Самооценка confidence от LLM не считается вероятностью или достаточным основанием автоматического принятия. Порог auto-accept возможен только после отдельной калибровки.

После реализации классификации темы документа в интерфейсе должны стать кликабельными: нажатие на тему открывает поиск документов с фильтром по этой теме, чтобы можно было перейти от текущего документа к другим документам той же тематики. Фильтр должен использовать присвоенные классификацией темы, а не подменяться обычным поиском слов.

## Последовательный whole-document pipeline

После применения миграции `0014_whole_document_batch.sql` отдельным администраторским действием запускать, например:

```sh
DATABASE_URL='...' python tools/nlp/whole_document_classify.py --batch v3-whole-01 --max-calls 500 --max-new-calls 2 --max-chars 30000
```

Новый batch фиксирует копию существующей выборки `v3-500-01` (ровно 500), отдельную версию pipeline, модель, лимит символов и SHA-256 taxonomy и prompt/schema. При возобновлении использовать те же параметры; несовпадение конфигурации блокирует запуск. `--max-calls` - пожизненный лимит включая ошибки и прерванные вызовы, `--max-new-calls` - лимит на текущий запуск. По умолчанию документы с более чем 30000 символов текста постов явно откладываются без отправки; это не токеновый лимит и не гарантия допустимого контекста провайдера. Все сохранённые посты и их ID отправляются вместе, без обрезки. Успешные v3 результаты с тем же полным hash пропускаются, в том числе пилотные документы 3 и 4; ручные события не изменяются. При прошлых failed документ может обрабатываться заново, ответы старых фрагментов остаются в журнале прежнего batch.

Каждый вызов сначала резервируется в `classification_call_attempts` и считается даже после аварийного завершения; успешный ответ сохраняется в журнале до транзакционной записи результата и может быть использован при возобновлении. На документ не более двух попыток в batch, при provider limit обработка останавливается; превышение лимита или исчерпание попыток требуют проверки. JSON-строки stdout и журнал БД позволяют проверить статусы, usage и ошибки; usage при аварии или таймауте может быть неизвестен. Advisory lock общий с chunk pipeline, но не защищает от сторонних программ, которые его не используют. Перед реальным запуском проверить разрешение на отправку данных, безопасность инструментов agy, стоимость и лимиты; sandbox не отключает встроенные инструменты. Применение миграции и запуск модели не выполняются автоматически.

## Оценка и безопасность

Сравнить с baseline micro/macro F1, per-topic precision/recall, долю отказов, evidence-validity, покрытие текста, latency/стоимость. Разделить dev/test по документам и связанным темам, не по chunks. Итоговая оценка на ручном holdout; LLM-метки не выдать за gold.

Текст форума — недоверенные данные: его инструкции не следует исполнять. В пилоте agy встроенные инструменты технически доступны; sandbox и пустой рабочий каталог снижают, но не устраняют риск. Генерация ограничена schema/allowlist, prompt не содержит секретов. Массовый прогон до отдельного решения после пилота не запускать; условия хранения и стоимость внешнего сервиса отдельно проверить. Автоматического обучения на корпусе нет.

Один и тот же document hash не прогонять повторно без смены pipeline. Классификацию выполнять фоном; страница и обычный поиск работают при выключенной модели.
