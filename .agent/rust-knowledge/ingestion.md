Номер RFC соответствует номеру PR, поэтому RFC 3058 не означает 3 058 документов. GitHub API использовался только для разведки объёма; в зачёт домашки собирается HTML сайта RFC, не скачанный репозиторий.

В [условиях Internals](https://internals.rust-lang.org/tos) указаны разные лицензии: для публикаций до 2020-07-17 — CC BY-NC-SA 3.0, с этой даты — MIT/Apache-2.0, если не указано иное. Сохранять авторство, URL, дату и сведения о лицензии на уровне публикации. Условия RFC и исключения проверять по [введению книги](https://rust-lang.github.io/rfcs/#license) и исходному материалу. Не объявлять весь объединённый корпус своей единой лицензией и не публиковать дамп автоматически.

## Пилот до основного сбора

1. Сохранить текущие robots, условия использования и дату проверки. Обрабатывать robots стандартным парсером; 5xx/сетевую ошибку не считать отсутствием правил.
2. Получить sitemap index и дочерние sitemap; извлечь разрешённые URL, нормализовать и исключить дубли. Не перебирать числовые ID.
3. Выбрать 100–200 тем разных лет, длин, категорий и 20–30 RFC. Часть тем должна быть длинной и с кодом.
4. Проверить обычный HTML-ответ без браузерной автоматизации: есть ли текст публикаций, даты, ссылки и навигация продолжения.
5. Проверить, не видна ли только первая часть длинной темы. Пагинацию обходить по фактическим разрешённым ссылкам; все страницы одной темы объединять под одним topic ID.
6. Если полный текст нельзя получить допустимым HTML-обходом, зафиксировать ограничение. JSON/API не подменяет требуемый HTML-сбор без согласования с преподавателем. Не придумывать ручки и не обходить ограничения доступа.
7. Оценить долю пустых, удалённых, служебных и дублирующихся материалов. Подтвердить достаточный запас для 5 000 пригодных тем.

## Политика нагрузки

- Собственный User-Agent с названием проекта и контактом; не выдавать себя за поисковый бот.
- Стартовая политика проекта: один запрос одновременно на домен, интервал 5–10 секунд. Это не опубликованный лимит источников и не гарантия отсутствия блокировок.
- Общий планировщик и пауза на домен, включая retries, robots и sitemap. Масштабирование парсинга/индексации не меняет внешний бюджет.
- Учитывать Retry-After, exponential backoff с jitter и конечным числом повторов. При 403/капче остановить источник для проверки; при 429 приостановить источник, при повторениях остановить запуск. Не менять IP для продолжения заблокированного обхода.
- Таймауты, ограничение размера ответа и числа редиректов. Проверять robots и allowlist для каждого назначения редиректа; не допускать запросы в локальные/служебные сети.
- Не скачивать видео, изображения, вложения, CSS/JS и профили для текстового корпуса. Не запрашивать поиск форума.
- Первичный сбор однократный, последующее обновление ограниченное; ETag/Last-Modified при наличии. HTML, контрольная сумма и версия парсера сохраняются.

6 000 запросов с паузой 5 секунд — около 8 ч 20 мин только интервалов; при 10 сек — 16 ч 40 мин. Пагинация и повторы увеличат число запросов. Не обещать 6 000 тем за это время.

## Конвейер и критерий документа

Discovery → очередь URL → проверка допуска → fetch → сохранение HTML → parse → нормализация → дедупликация → canonical JSONL + JSON/CSV + manifest → PostgreSQL/outbox и Tantivy. Фоновые производные: леммы, AI-теги, chunks/Qdrant, граф; сбой ML не мешает экспорту и baseline-поиску.

Для каждой загрузки: запрошенный и итоговый URL, canonical, HTTP status, время, content type, hash, путь HTML, попытка, версия парсера. Cookie/токены не журналировать.

Internals: topic ID, заголовок, категория/теги при наличии, даты, публичный автор публикации, post ID, текст, код, цитаты, ссылки, признак полноты. Не собирать профиль автора и контактные сведения.

RFC: номер, feature name, дата, заголовок, разделы, код, исходящие ссылки на обсуждение/issue, связанные RFC. Статус реализации по факту наличия RFC не выводить.

Удалять навигацию, меню и повторяющиеся цитаты из поискового представления, сохраняя оригинал. Код хранить отдельно от прозы. Дедупликация по ID/canonical и content hash; похожие обсуждения не сливать лишь по общей теме.

В зачёт идёт уникальная тема с успешно полученным HTML и полезным основным текстом. До массового сбора зафиксировать порог содержательности по пилоту (начальное предложение: 200 символов содержательного текста без меню) и правило полноты. Частичные темы хранить с пометкой, но не включать в строгий приёмочный минимум. Не называть такой порог гарантией качества: требуется ручная выборочная проверка.
